FIREWALLDO PORTAL — CONTRATO 1.5

Frontend: React 18, TypeScript, Vite. Backend: Java 17 / Spring Boot / PostgreSQL.
Os tipos de negócio ficam em src/types/models.ts. Os serviços ficam em src/services/index.ts.

MODO API
VITE_DATA_SOURCE=api
VITE_API_URL=/api
Use o mesmo domínio do portal. O Caddy encaminha /api/* para API_UPSTREAM;
o Vite encaminha /api/* para localhost:3333 no desenvolvimento local.

AUTENTICAÇÃO
POST /api/auth/login: {email, senha}. Responde {user} e cookie HttpOnly.
GET /api/auth/me: perfil autenticado, sem senha/hash.
POST /api/auth/logout: {}. Encerra a sessão.
POST /api/auth/activate: {token, senha}. Compatibilidade com convites antigos.
A sessão fica no cookie; não existe token de acesso no localStorage.

CONTAS
GET /api/users
POST /api/users: {name, email, role, title, senha, bio?, areas?}
PATCH /api/users/:id: campos de perfil e, opcionalmente, senha,
confirmacaoSenha e senhaAtual. A confirmação é obrigatória ao definir nova
senha na edição. senhaAtual é obrigatória para alterar o próprio e-mail/senha.
Senha de 12 a 128 caracteres. Criação exige apenas um campo de senha.

Perfis: superadmin (Administrador geral), admin (Administrador), usuario (Usuário).
O geral administra todas as contas. Admin administra apenas usuários comuns.
Cada pessoa pode editar a própria conta; não pode se promover por esse meio.
Somente gerais criam/promovem administradores. O último geral ativo com senha
não pode ser desativado/rebaixado. Mudanças sensíveis revogam outras sessões.

AUDITORIA
GET /api/audit?q=&action=&entity=&outcome=&from=&to=&page=1
Apenas admin/superadmin. Não basta ocultar a aba; a API devolve 403 ao usuário.
Resposta: {items, total, page, pageSize:50}.
Item: id, createdAt (ISO), actorId, actorName, actorEmail, action, entity,
entityId, targetName, ip (ou null), outcome, details.
Ações: criacao, edicao, exclusao, login, logout, ativacao, acesso.
Resultados: sucesso, falha, bloqueado.
Datas do filtro e exibição: America/Sao_Paulo.
Eventos de negócio são inseridos por gatilhos na mesma transação da alteração;
falhas de autenticação/acesso são registradas separadamente. O autor vem da
sessão no servidor. Não são enviados autor/IP pelo corpo do formulário.
Falhas de login mostram Sistema como autor e a conta informada como alvo,
pois o e-mail digitado não prova a identidade de quem tentou entrar.
Senhas, hashes, tokens e cookies nunca são incluídos nos registros.
Não existem endpoints para editar ou apagar o histórico.

PREFERÊNCIAS
GET/PUT /api/me/preferences persiste tema, animações e preferências de notificações por conta. Claro/escuro/sistema são aplicados ao selecionar e salvar na API. Sistema acompanha prefers-color-scheme.

LIMITES ATUAIS
O Radar publica manualmente e por coleta agendada via OpenAI. RSS automático não está integrado.
Biblioteca tem upload/download PostgreSQL (5 MB), consulta e exclusão auditadas. Sincronização Drive e e-mail externos não estão configurados. Web Push foi incluído na revisão 1.5. E-mail está desabilitado na interface e é recusado pela API. Notificações no portal e lembretes de prazo estão implementados.
A auditoria cobre novas ações após a migração V2, sem reconstruir o passado.

POST /api/settings/radar/collect: trabalho em segundo plano (202 + runId).
OPENAI_API_KEY somente no servidor; OPENAI_MODEL opcional. Não há formulário para enviar a chave ao navegador.

WEB PUSH (V5)
GET /api/push: publicKey, devices e deliveries da conta.
POST /api/push/subscriptions: {id,endpoint,keys:{p256dh,auth},device}.
DELETE /api/push/subscriptions/:id: remove aparelho próprio.
POST /api/push/test: aviso real na fila de envio (202).
VAPID é gerado pela API e persistido; só a chave pública vai ao navegador.
O cliente envia X-Push-Device; logout revoga essa inscrição da conta. O Service Worker é /sw.js, sem cache de conteúdo autenticado. Manifesto em /manifest.webmanifest. Push precisa de HTTPS e autorização por aparelho. No iPhone, é necessário abrir a instalação na Tela de Início.


AGENDA E TICKETS — V1.7
GET /agenda: regras, próximas seis aberturas; usuário recebe apenas regras próprias.
POST /agenda: criar; PUT /agenda/:id: editar; PATCH /agenda/:id/active {active}; DELETE /agenda/:id: remover regra sem excluir tarefas liberadas. Escritas restritas a admin e superadmin.
Campos: title, description, projectId (nullable), category, priority, assigneeIds (1–100), kind (recurring/weekly/scheduled), intervalDays (1–365), startDate (ISO), endDate (nullable), openingTime (HH:mm Brasília), weekdays (1=segunda ... 7=domingo), dates (até 100 datas ISO), deadlineDays (0–365), checklist.
A API cria uma tarefa por pessoa ativa a cada abertura; próximos horários são somente prévias. Cada cópia tem scheduleId e scheduledFor para rastreio.
GET /tasks restringe usuário às próprias tarefas. Filtro assigneeId de outra conta é 403 para usuário; admin/superadmin consultam todos ou um responsável.
Todas as tarefas retornam ticketNumber: inteiro global e imutável, atribuído pelo banco ao criar; exibir como ticket01/ticket02/.../ticket405. Não enviar esse campo em PATCH. Regras não recebem ticket antes da liberação. Tarefas removidas não têm número reutilizado.

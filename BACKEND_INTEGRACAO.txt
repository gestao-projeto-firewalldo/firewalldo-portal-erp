=====================================================================
 FIREWALLDO · PORTAL DE DESENVOLVIMENTO
 Guia do Front-end para quem vai construir o Back-end   (Front-end V1.2)
=====================================================================

Este arquivo explica como o front-end funciona e EXATAMENTE o que ele espera
da API. Foi escrito para ser lido por uma pessoa ou colado em um assistente de
IA (ChatGPT, Claude etc.) como contexto para gerar o back-end.

Resumo em uma frase:
  O front já está pronto e funciona sozinho com dados simulados; para ligar no
  back-end basta implementar as rotas REST listadas na seção 6, devolvendo JSON
  no formato dos tipos da seção 5, e iniciar o front com VITE_DATA_SOURCE=api.


---------------------------------------------------------------------
 1. STACK E COMO RODAR
---------------------------------------------------------------------
- React 18 + TypeScript + Vite 6 + React Router 6 + lucide-react (ícones).
- Sem framework de UI; CSS próprio em src/styles.
- Node 18+ (testado com Node 26).

  npm install
  npm run dev        -> http://localhost:5173
  npm run build      -> checagem de tipos + build de produção em dist/

O build gera arquivos estáticos (dist/). Pode ser servido por qualquer servidor
estático. Como usa rotas no navegador (BrowserRouter), o servidor deve devolver
index.html para qualquer caminho desconhecido (fallback de SPA).


---------------------------------------------------------------------
 2. MODO DEMONSTRAÇÃO x MODO API
---------------------------------------------------------------------
Arquivo: src/config.ts

  VITE_DATA_SOURCE = mock (padrão) | api
  VITE_API_URL     = URL base da API (padrão: http://localhost:3333/api)

Crie um arquivo .env na raiz do front:

  VITE_DATA_SOURCE=api
  VITE_API_URL=http://localhost:3333/api

- mock: usa os dados de src/mocks/data.ts, com atraso artificial de 250–650 ms
  e persistência apenas no localStorage do navegador (chave firewalldo-portal:v3).
  NADA disso é banco de dados; serve só para demonstrar as telas.
- api: todas as telas passam a chamar a API real. As telas NÃO mudam.


---------------------------------------------------------------------
 3. ARQUITETURA (onde mexer)
---------------------------------------------------------------------
src/
  types/models.ts       CONTRATO DE DADOS. Formato de todos os objetos.
  services/index.ts     ÚNICO lugar que busca/grava dados. Cada método tem:
                          if (useApi()) return http.<verbo>('/rota', corpo)
                          senão -> usa o mock
                        Procure por "TODO(api)": cada um indica a rota esperada.
  services/core.ts      Cliente HTTP (fetch), simulação do mock, utilitários.
  mocks/data.ts         Dados fictícios (servem de EXEMPLO do JSON esperado).
  context/SessionContext.tsx  Usuário logado, lista de usuários/projetos e
                        a matriz de permissões por perfil (rolePermissions).
  hooks/useQuery.ts     Estados de carregando / erro / dados das telas.
  pages/                Telas (Início, Radar, Ideias, Projetos, Tarefas,
                        Usuários, Configurações; Biblioteca e Relatórios
                        existem fora do menu).
  components/           Layout (menu/cabeçalho), modal de tarefa, UI.

Fluxo de dados:
  Tela -> useQuery(() => xxxService.metodo()) -> services/index.ts -> http -> API
  Depois de qualquer POST/PATCH/PUT/DELETE bem-sucedido, o cliente HTTP dispara
  um aviso global e todas as telas abertas recarregam seus dados em segundo
  plano (não precisa implementar nada para isso).


---------------------------------------------------------------------
 4. CONVENÇÕES DA API
---------------------------------------------------------------------
- JSON em UTF-8, nomes de campos em camelCase (exatamente como na seção 5).
- IDs são STRINGS (ex.: "u-victor", "t-12", ou UUID). Não use número.
- Datas sem hora: "AAAA-MM-DD" (ISODate). Ex.: "2026-11-20".
- Campos opcionais podem vir ausentes; listas vazias devem vir como [].
- Sucesso: 200/201 com JSON. Sem corpo: 204 No Content (o front aceita).
- Erro: status 4xx/5xx com corpo JSON:
      { "message": "Texto para mostrar ao usuário", "code": "NO_SLOTS" }
  O front mostra "message" num aviso na tela. Códigos usados pelo front:
      NOT_FOUND (404), CONFLICT (409), NO_SLOTS (409), FORBIDDEN (403).
- Autenticação: o cliente envia
      Authorization: Bearer <token>
  se existir um token salvo no localStorage com a chave "fw:token".
  (A tela de login ainda não existe. Ver seção 9.)
- CORS: liberar a origem do front (em dev: http://localhost:5173) e os
  cabeçalhos Content-Type e Authorization.

---------------------------------------------------------------------
 6. ROTAS ESPERADAS (todas relativas a VITE_API_URL)
---------------------------------------------------------------------
Formato:  MÉTODO  /rota   corpo  ->  resposta   [quem pode]

SESSÃO
  GET    /auth/me                         -> Member (usuário logado)      [logado]

USUÁRIOS
  GET    /users                           -> Member[]                     [logado]
  POST   /users        MemberInput        -> Member (201)                 [admin]
         MemberInput = { name, email, role, title }
         409 CONFLICT se o e-mail já existir. Envio de convite/senha é do back.
  PATCH  /users/:id    { name?, title?, bio?, role?, active?, areas? } -> Member
         [admin; ou o próprio usuário para name/title/bio]

PROJETOS
  GET    /projects                        -> Project[]                    [logado]
  GET    /projects/:id                    -> Project  (404 NOT_FOUND)     [logado]
  POST   /projects     { name, subtitle, description, icon, color, dueDate, ownerIds }
                                          -> Project (201)                [admin]
  PATCH  /projects/:id/milestones/:milestoneId   (alterna done)  -> Project [admin]

TAREFAS
  GET    /tasks                           -> Task[] ordenado por "order"  [logado]
         (filtros opcionais futuros: ?projectId=&assigneeId=&status=)
  POST   /tasks        TaskInput          -> Task (201)                   [admin]
  PATCH  /tasks/:id    Partial<Task>      -> Task
         [admin: qualquer campo | responsável: status e checklist]
         O checklist é salvo por esta mesma rota: { "checklist": [...] }
  PATCH  /tasks/:id/move  { status, beforeId }  -> 204
         Move de coluna. beforeId = id da tarefa que ficará logo abaixo
         (null = final da coluna). Recalcular "order" da coluna.
         [admin: qualquer | usuário: só tarefas em que é responsável]
  POST   /tasks/:id/accept                -> Task                         [logado]
         Usuário logado aceita uma vaga. Regras na seção 7.
         409 NO_SLOTS se não houver vaga ou a tarefa não estiver aberta.
  POST   /tasks/:id/leave                 -> Task  (sai da tarefa)        [logado]
  DELETE /tasks/:id                       -> 204                          [admin]

RADAR DE NOTÍCIAS
  GET    /news                            -> NewsItem[]                   [logado]
         Notícias coletadas SOMENTE das fontes com active=true.
  GET    /news/saved                      -> string[] (ids salvos pelo usuário)
  POST   /news/:id/save                   -> string[] atualizado (alterna salvar/remover)

IDEIAS
  GET    /ideas                           -> Idea[]  (votedByMe por usuário logado)
  POST   /ideas        IdeaInput          -> Idea (201; status "nova", votes 0)
  PATCH  /ideas/:id    { status }         -> 204 ou Idea                  [admin]
  POST   /ideas/:id/vote                  -> 204   (alterna "Gostei"; 1 voto por usuário)

NOTIFICAÇÕES
  GET    /notifications                   -> AppNotification[] (do usuário logado)
  POST   /notifications/read-all          -> 204

CONFIGURAÇÕES (aba Integrações)
  GET    /settings/radar-sources          -> RadarSource[]                [logado]
  PUT    /settings/radar-sources  RadarSource[]  -> RadarSource[]         [admin]
         Recebe a LISTA INTEIRA (ativar/pausar, adicionar). Ids novos criados no
         front começam com "src-"; o back pode trocar por ids próprios.
  GET    /settings/shortcuts              -> Shortcut[]                   [logado]
  PUT    /settings/shortcuts      Shortcut[]     -> Shortcut[]            [admin]

AINDA SÓ LOCAL (não chamam API hoje; ligar quando existir)
  - Preferências pessoais (tema, notificações): salvas no navegador.
    Sugestão: GET/PATCH /me/preferences -> UserPreferences.
  - Biblioteca (fora do menu): GET /library/folders, GET /library/files,
    upload futuro POST /library/files (multipart) -> Google Drive.
  - Relatórios (fora do menu): calculados no front a partir de /tasks e /projects.


---------------------------------------------------------------------
 7. REGRAS DE NEGÓCIO (o servidor deve validar; o front só ajuda)
---------------------------------------------------------------------
TAREFAS / KANBAN
- Colunas: backlog -> a_fazer -> em_andamento -> concluido.
- "Backlog" = vagas abertas. Uma tarefa aparece com botão "Aceitar tarefa"
  quando open=true. O cartão mostra "Lim. X/Y" = assigneeIds.length / maxAssignees.
- Aceitar (POST /tasks/:id/accept):
    1. exige open=true e assigneeIds.length < maxAssignees (senão 409 NO_SLOTS);
    2. adiciona o usuário logado em assigneeIds (sem duplicar);
    3. se lotar (length == maxAssignees): open=false e, se estava em backlog,
       status passa para "a_fazer".
- Tarefas são criadas por ADMIN dentro de um projeto (tela do projeto ->
  "Criar tarefa"). A tela Tarefas tem o link "Criar tarefa em Projetos".
- Arrastar entre colunas: admin move qualquer tarefa; usuário só as suas.
- "order" define a posição dentro da coluna (1, 2, 3...).

PROJETOS
- Progresso exibido = tarefas concluídas / tarefas do projeto (arredondado).
  Se o projeto não tiver tarefas, o front usa o campo "progress".
  Sugestão: devolver "progress" já calculado com esta regra.
- "X de Y tarefas concluídas" também é calculado com /tasks.

IDEIAS
- Novas ideias nascem com status "nova" e 0 votos.
- Filtros da tela: Todos | Em análise | Aprovadas, + Categoria.
- Só admin muda status. Ideia "aprovada" pode virar tarefa (o front abre o
  formulário de tarefa preenchido; a criação usa POST /tasks).

USUÁRIOS
- Perfis: admin ("Administrador") e usuario ("Usuário").
- "Online agora" conta active=true e status="online". A regra de presença
  (ex.: atividade nos últimos 5 min, WebSocket) é decisão do back.
- Usuário desativado (active=false) continua listado, esmaecido.

RADAR
- As notícias atuais são FICTÍCIAS (isDemo=true). Com a coleta real, mande
  isDemo=false e preencha "source" com o nome da fonte e "url" com o link.
- "featured": o front mostra a primeira notícia destacada no topo.

PERMISSÕES (src/context/SessionContext.tsx -> rolePermissions)
  Permissão                    admin  usuario
  tarefas.criar                  x
  tarefas.editar_todas           x
  tarefas.aceitar                x       x
  projetos.gerenciar             x
  biblioteca.enviar              x       x
  usuarios.gerenciar             x
  noticias.curar                 x
  relatorios.ver                 x       x
  configuracoes.integracoes      x
  O front ESCONDE botões conforme o perfil, mas a API deve recusar (403
  FORBIDDEN) qualquer ação sem permissão.
